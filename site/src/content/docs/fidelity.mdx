The port is checked against C Graphviz 16.1.0 in four ways, from the strictest to the broadest. All the corpus checks run in `cargo test --workspace` as ratchets: each has a committed baseline listing the files that match, and a file that stops matching fails the build. The numbers on this page are read from those runs and baselines by `scripts/site-data.py`; none are typed in by hand, except where marked.

Two math profiles are reported. **macOS** uses Apple's libm, as C does on the reference machine. **Linux and WASM** use a portable math library, because Apple's `pow`, `sin`, `cos` and `atan2` are closed source and not reproduced bit for bit there; Linux on aarch64, Linux on x86_64 and the WASM build give the same bytes as each other ([why](/graphvis-rs/porting/libm/)).

## Full pipeline

`gv-diff e2e` runs the whole port, parse to layout to render, on every input of nine corpora and compares its `-Tsvg` output with C's. **Identical means equal bytes**, after dropping the one line that starts with `<!-- Generated by `, which names the program and its version. Nothing else is normalised.

Only hashes of C's output are committed (`tests/golden/e2e.json`, 64-bit FNV-1a of the normalised SVG), so the check runs without C installed. Each C reference was produced twice; inputs whose C output differed between the two runs are recorded as unstable and skipped.

### Is it only the math library?

Yes. Running C itself with the port's portable math functions (`scripts/dot-portable-libm.sh` loads them into the unmodified C `dot`) and comparing again:

| | vs stock C on macOS | vs C with the port's math functions |
| :--- | ---: | ---: |
| Linux and WASM build | 2,470 / 2,589 | **2,590 / 2,590** |
| C Graphviz built on Linux, for comparison | 2,005 / 2,586 | — |

With the same math functions on both sides, the browser build is byte-identical to C on every stable input; a ratchet in CI keeps it that way. C itself is less consistent across platforms than the port: built on Linux the way Homebrew builds it on macOS, it matches macOS C on 77.5% of the corpus, against 95.4% for the port in the browser. The details, and what makes Linux C differ (glibc's math, `qsort` and `rand`), are in [Math off macOS](/graphvis-rs/porting/libm/).

## Layout

`gv-diff` (without `e2e`) compares geometry rather than bytes: it lays out each input with the port, reads C's `-Tdot` output for the same input, and checks the bounding box, every node's centre and size, every edge's spline, arrow endpoints and label positions, and every cluster box. A file is **exact** when every element is within tolerance: 1 pt for node positions, sizes and bounding boxes, 2 pt for edge splines (sampled Hausdorff distance) and labels. This is looser than byte identity, and it covers the per-engine corpora with C goldens kept as `.dot` files (`tests/golden/<engine>/`).

<LayoutTable />

The 7 twopi files are a floating-point tie in edge routing that C itself breaks differently from run to run, so no fixed reference can match every C. The full-pipeline check skips the same inputs as unstable.

## Renderers

`gv-diff render` takes C's own layouts (`tests/golden/render/laid/*.dot`) and renders them with the port in no-layout mode (`-Kneato -n2`), next to C's renderings of the same layouts. Any difference comes from the output code (or node sizing, which `-n2` recomputes). Identity is byte for byte, generator comment aside.

<RenderTable />

The skipped `-Tplain` and `-Tplain-ext` references are ones C does not reproduce from run to run: for some converted labels C prints a string after `lib/common/output.c` has freed it, so the field holds whatever is left in that memory. The two that differ hit the same path; on the reference machine C prints an empty label there, while the port prints the label.

## C test graphs

`scripts/dot-broad-validate.sh` lays out every graph in the Graphviz 16.1.0 source tree (`graphs/`, `tests/graphs/`, `tests/regression_tests/`) with C and with the port, in five variants, and `gv-diff pairs` compares the layouts as above.

## Fuzzing

The corpora only contain inputs someone thought of. `scripts/fuzz-gen.py` generates random graphs from a seed (engine, size, topology, clusters, rank sets, attributes from the whole Graphviz table, and about 8% malformed input), and `scripts/fuzz-run.py` runs C and the port on each and compares stdout (generator comment aside) and exit status. Every difference was minimised and fixed against the C source, round by round; one reproducer per bug went into the corpus.

Identity is the share of comparable cases whose output and exit status both match C. Cases where C's output changes between two runs, C times out, or C crashes are excluded.

<FuzzRounds />

Read from the rounds table in [the fuzzing notes](/graphvis-rs/porting/fuzzing/), which also break down the remaining differences: mostly C nondeterminism (layouts that depend on heap addresses), C undefined behaviour on inputs it reports as invalid, and a few open differences, which are tracked in [What's left](/graphvis-rs/whats-left/).

## The reference

C Graphviz 16.1.0, run with `GVBINDIR` pointing at a plugin directory that holds only its core, dot and neato plugins. With no Pango text-layout plugin available, C measures text with its built-in font metric tables, as the port does. A default installation, which measures text with Pango and cairo, will not match. [Set it up yourself](/graphvis-rs/verify/#the-c-reference).
